00 · Executive summary

摘要

单轮 RLVR 中，response 通常直接对应一个可验证 outcome；multi-turn agent 则包含 planning、tool call、verification 和 revision，后续 state 还受前序 action 与环境共同影响。训练若只提供 terminal reward，很难判断各 turn 的真实贡献。
引入 intermediate reward 又要求 verifier 可靠且不易被利用。同时，搜索、judge、执行与 profiling 成本会随 turn 数放大，因此 credit assignment 必须与环境成本一起设计

四篇工作的处理方式

AgentFlow 只训练 Planner，把 terminal advantage 广播到它的所有 turns

StitchCUDA 把 multi-turn workflow 拆成两类单轮任务，改用 single-turn GRPO

ReVeal 交替生成代码和测试，并按执行结果分配每轮奖励

SAO 面向异步与 online 场景改用 single-rollout actor-critic，成败取决于 critic 质量

01 · AgentFlow

AgentFlow：Planner-only RL 与 trajectory broadcast

arXiv 2510.05592v2

Motivation：让模块化 agent workflow 能从任务结果中学习调度

方案组织方式主要问题
Monolithic tool-use RL一个 policy 同时完成 reasoning 和 tool callshorizon 变长、工具增多后，rollout 和训练更不稳定
Modular agent workflow分离 planning、execution 和 verification依赖 frozen model 与手写 orchestration，无法从最终结果学习模块协作

AgentFlow 提出：保留模块化设计，但只把负责调度的 Planner 放入 multi-turn rollout 中做 on-policy RL，以此连接“可训练的 monolithic policy”和“灵活但静态的 agent workflow”

为什么只训练 Planner

每个 turn 中，Planner 决定当前 sub-goal、选择哪个 tool，以及从 memory 中取哪些 context；这些动作决定后续会访问什么信息、状态如何变化，是 workflow 中连续做策略决策的模块

AgentFlow 将 Planner 视为 RL policy，把 Executor、Verifier、Generator、tools 和 memory update 视为 environment 并保持 frozen。这样可以把 joint multi-module training 收缩为单 policy optimization，减少多个模块同时更新造成的 non-stationarity

Memory 由规则更新，不是第五个 agent

\(M^1\) 由原始 query 初始化。每个继续执行的 turn 结束后，确定性的 \(f_{\mathrm{mem}}\) 将旧 memory、Planner action、tool execution result 和 verifier signal 写成下一轮状态：\(M^{t+1}=f_{\mathrm{mem}}(M^t,a^t,e^t,v^t)\)

实现中没有专门的 memory agent，也不调用另一个 LLM 做摘要。系统用正则表达式解析各 module 的标准化输出，提取 Planner 的 Sub-Goal 与 Tool Name、Executor 的 Command、Query 与 Result，以及 Verifier 的分析和 CONTINUE / STOP，再按 turn 顺序追加为结构化记录

Flow-GRPO 先做 group normalization，再 broadcast

对同一 prompt 采样 \(G=8\) 条 trajectories，每条最终答案由 GPT-4o judge 给出 binary outcome，组内 reward 经均值与标准差归一化为 trajectory advantage，然后同一个 advantage 赋给该 trajectory 中所有 turn 和 token，objective 再按 \(1/T_i\) 与 \(1/|a_i^t|\) 归一化

02 · StitchCUDA

StitchCUDA：拆成 single-turn 任务，避免 full-trajectory RL

arXiv 2603.02637v2

Motivation：需要训练 Coder，但完整 agentic rollout 成本过高

方案能解决什么主要问题
Prompt-only multi-agent提供 planning、profiling 与结构化 feedbackCoder 参数不更新，仍难以执行复杂的 targeted optimization
Single-turn RL用 correctness 与 speedup 训练代码生成容易 reward hacking，也没有训练 Coder 如何使用 profiler feedback
Full multi-turn agentic RL直接训练 feedback-driven refinement每轮都要编译、验证和 profiling，完整 rollout 成本过高

StitchCUDA 提出：从 workflow 中抽出两类反复出现的单轮任务：from-scratch generation 与 feedback-driven optimization，只用 400 条 single-turn episodes 训练 Coder

方法：推理仍是多轮，只训练 Coder

  • Planner · GPT-5.2RAG + profiling harness，拆解 fusion、layout 与 overlap 计划，保持 frozen
  • Coder · Qwen3-32B唯一被训练的 agent，single-turn GRPO + LoRA r=128
  • Verifier · GPT-5.2 + toolscorrectness gate 与 Nsys → NCU bottleneck route，产生结构化 feedback

两类单轮任务 + execution × rubric reward

训练目标是 Coder 在 workflow 里反复做的两类单轮任务，各自独立构造样本、独立打分：

  • 任务 1 · from-scratch generation对应 workflow 第一轮：根据 task requirements 和 reference PyTorch code，从零生成完整 CUDA implementation
  • 任务 2 · feedback-driven optimization对应后续每一轮：根据现有 code 和 verifier feedback，做 targeted optimization

训练分三步，全程只跑单轮、不启动完整 workflow：

  • 1 · 收集 episodes任务 1：从 KernelBench Level 1–3 随机抽 80% 题目，由 Planner 拆成子任务、人工筛选，得 200 条；任务 2：在同一批题目上跑 workflow 收集 verifier 的 (code, feedback) 对，只保留"按 feedback 修改后下一轮 kernel 正确"的实例，得 200 条
  • 2 · 单轮 GRPO每条 episode 一次 prompt → 一次 response，按下方的 execution × rubric reward 更新 Coder（GRPO + LoRA r=128）
  • 3 · 放回 workflow训练后的 Coder 替换回原多轮 workflow：首轮写 kernel 对应任务 1，后续吃 profiling feedback 改 code 对应任务 2
\[ R=\mathbb I_{\mathrm{corr}}(1-\mathbb I_{\mathrm{hack}}) \min\!\left[(\mathrm{speedup}+0.3)(1+\hat r_{\mathrm{rubric}}),5\right] \]

Rubric：四个维度，judge 打分，乘性 shaping

Rubric 由 CUDA 专家起草、GPT-5.2 协助润色并离线验证；训练时由 Qwen3-32B judge 对每个候选按四个维度各自打分

  • Anti-Hacking惩罚 reward exploitation：PyTorch-only code（如包一层 nn.ConvTranspose3d 冒充 kernel）与 hardcode output
  • CUDA Engineering奖励高级 CUDA 技术：shared memory tiling、异步 memcpy、cuBLASLt、CUTLASS、tensor core 的 wmma 指令、kernel fusion、混合精度、inline PTX
  • Operator Coverage鼓励覆盖尽量多算子（含 host-side 优化），抑制"只写个 ReLU 就交差"的 degenerate 行为
  • Skill Compliance任务 1 看是否遵守 task requirements，任务 2 看是否遵循 feedback instructions

03 · ReVeal

ReVeal：turn-aware reward 与 TAPO

arXiv 2506.11442v2

Motivation：把 self-verification 从隐式行为变成训练目标

方案Verification signal主要问题
Outcome-only RLVR只看最终答案是否正确中间 verification 没有被直接优化，困难问题上容易退化为无效反思或猜测
Separate critic额外模型评价每次尝试增加 inference cost，而且没有利用真实 tool execution feedback
Pre-existing tests执行公开测试用例现实任务通常没有可直接使用的 public tests

ReVeal 利用 verification-generation asymmetry：验证一段 code 往往比写出它更容易。同一个 policy 交替扮演两个角色——生成 code、再生成 tests，用 tests 的执行结果指导下一轮修订；并把写 code"和"写 tests"两种行为都纳入训练

算法流程：生成 code、生成 tests，再根据执行结果修订

  • 1 · Generation同一个 policy 根据题目与历史 context 生成 candidate code
  • 2 · Verificationpolicy 针对当前 code 构造可执行 tests，用于覆盖边界条件和潜在错误
  • 3 · Tool feedback执行 tests，记录 expected output、actual output、异常与 pass / fail，并把结果写回下一轮 context
  • 4 · Revision下一次 generation 根据执行反馈修改 code；流程重复到得到有效解或耗尽 turn budget

TAPO：先定义三类 reward，再构造 turn-aware advantage

TAPO（Turn-Aware Policy Optimization）的核心思想：整条 rollout 只有一个最终结果，但每个 turn 都有可验证的中间信号。而TAPO 把两类信号放进两条独立的 reward channel，分别计算

记号：\(k\) 是 turn index（奇数 turn 生成 code，偶数 turn 生成 tests）；\(t\) 是整条 rollout 的 token index；\(p^k\) 是第 \(k\) 个 generation turn 的 code 在 ground-truth tests 上的 passrate

1. 三类 verifiable reward

Reward作用位置公式含义
OutcomeToken-level channel，整条 trajectory\(r_{\mathrm{out}}=r_{\mathrm{format}}+5p_{\mathrm{final}}\)评价输出格式和最终 code 的 ground-truth test passrate
GenerationTurn-level channel，当前 generation turn\(r_{\mathrm{gen}}^1=p^1\)
\(r_{\mathrm{gen}}^k=p^k-p^{k-2}\)		首版看 absolute passrate，后续只奖励相对上一版 code 的改进
VerificationTurn-level channel，当前 verification\(r_{\mathrm{ver}}^k=N_{\mathrm{pass\text{-}golden}}/N_{\mathrm{generated}}\)评价自生成 tests 在 golden code 上是否成立

2. Token-level return：只传播最终 outcome reward

即把最终结果广播给整条 trajectory，time discount=1。

3. Turn-level return：按 turn 角色分配中间 credit

只放 generation / verification rewards，同一个 turn 内的所有 tokens 共享同一个 return：

\[ R^{\mathrm{turn}}(k)= \begin{cases} r_{\mathrm{gen}}^k, & k\text{ is a generation turn} \\ r_{\mathrm{ver}}^k+r_{\mathrm{gen}}^{k+1}, & k\text{ is a verification turn} \end{cases} \] 若 verification 后没有下一次 generation，则第二项为 0；同一 turn 内的所有 tokens 共享对应的 \(R^{\mathrm{turn}}(k)\)

4. 合成 advantage，再进入标准 PPO update

用完整 rollout 的真实结果而不是 value model 的预测，bias 小但 variance 大；因此 critic 仍保留，在最后一步作为 baseline：\(A_t=\widetilde R_t-V_t\)

\[ \widetilde R_t=R_t^{\mathrm{outcome}}+R^{\mathrm{turn}}\!\bigl(k(t)\bigr), \qquad A_t=\widetilde R_t-V_t \]

04 · SAO

SAO：single-rollout 的异步 actor-critic

arXiv 2607.07508v1

Motivation：GRPO 的 group rollout 不适合异步 agentic 训练

  • Latency 加剧 off-policygroup 要等最慢的一条完成才能进入训练，数据生成时 policy 已经漂移，policy-lag 被放大
  • Online 场景没有 group真实线上环境每个 prompt 只返回一条 trajectory 反馈，组内统计 baseline 在数学上不可行

SAO（Single-rollout Asynchronous Optimization）是智谱面向 agentic RL 的工业级方案，已用于 GLM-5.2 与 GLM-5.3 的训练。它回到 single-rollout actor-critic：一条轨迹生成完立刻进训练，不等同伴。代价是失去 group baseline，variance 控制全部压回 value model，critic 的训练质量因此成为成败关键

DIS：只用两个 policy 的双边 clipping

解耦式 PPO 的异步实现通常维护三个模型，用两段 ratio 分别校正两类偏差，代价是 old-policy 要单独推理一次；异步场景下轨迹生成期间模型可能已更新多次，精确的 old-policy 还需要保留 checkpoint 历史。DIS（direct double-sided importance sampling）只保留首尾两个 policy：

\[ \text{decoupled PPO:}\quad \underbrace{\frac{\pi_\theta}{\pi_{\theta_{\mathrm{old}}}}}_{\text{stale 校正}} \cdot \underbrace{\frac{\pi_{\theta_{\mathrm{old}}}}{\pi_{\mathrm{rollout}}}}_{\text{mismatch 校正}} \qquad\Longrightarrow\qquad \text{DIS:}\quad r_t(\theta)=\frac{\pi_\theta(a_t\mid s_t)}{\pi_{\mathrm{rollout}}(a_t\mid s_t)} \] 分子来自 training forward，分母直接复用 rollout 阶段保存的 log-prob，省掉 old-policy recomputation

Clipping 方式也不同：PPO 只在悲观方向截断（\(\hat A>0\) 且 ratio 过大，或 \(\hat A<0\) 且 ratio 过小，另一侧梯度照常通过）；DIS 两个方向越界都把 token 整体 mask 出梯度

\[ \text{PPO:}\quad \begin{cases} \hat A_t>0: & \min\!\bigl(r_t,\ 1+\epsilon\bigr)\,\hat A_t \\[4pt] \hat A_t<0: & \max\!\bigl(r_t,\ 1-\epsilon\bigr)\,\hat A_t \end{cases} \] \[ \text{DIS:}\quad \mathcal L=\mathbb E_t\bigl[f(r_t)\,\hat A_t\log\pi_\theta(a_t\mid s_t)\bigr], \qquad f(x)= \begin{cases} x, & 1-\varepsilon_l \lt x \lt 1+\varepsilon_h \\ 0, & \text{否则} \end{cases} \] PPO 只截断悲观方向：\(\hat A>0\) 时封顶 \(1+\epsilon\)，\(\hat A<0\) 时兜底 \(1-\epsilon\)，另一方向不限制；DIS 的 \(f\) 在两侧越界都直接清零

信任区间设得非常宽：数学任务 \((0.7,\,6.0)\)，coding agent \((0.2,\,4.0)\)。宽区间能 work 的前提是 critic 给出的 advantage 足够准，错误的优势估计不会被逐 token 的 ratio 进一步放大

Critic 的三个工程优化

  • 更新更勤policy 每更新 1 次，value network 更新 K=2 次；value lr 5e-6 高于 policy lr 1e-6
  • Value pretrain先用大规模语料预训练 value model，消除冷启动；没有 pretrain 时早期 advantage 噪声会直接毒化 policy
  • Frozen attentionRL 期间冻结 critic 的 attention 参数，只训 MoE projection；pilot 实验发现 critic 梯度不稳定主要来自 attention 层，预训练的 attention 已具备足够的语义聚焦能力

结果：稳定训练约 1000 步，收敛优于 GRPO

Backbone 为 Qwen3-30B-A3B-Thinking。对照组中 vanilla GRPO 约 160 步崩溃、VAPO 约 90 步崩溃；SAO 稳定训练约 1000 步，400 步后与 GRPO（w/ DIS）明显分叉

Open question

方法简单、阈值宽松，为什么 work 得这么好

实验只覆盖单一 backbone（Qwen3-30B-A3B）、一个 coding benchmark 和受控模拟的 online 场景，无法深入归因。两个候选解释：

  • Infra 消除了 mismatchGLM 的 RL infra 本身足够好，rollout 与训练的偏差已被工程消除大半，宽 clipping 放过的极端 token 本来就不多，代价随之变小
  • Critic 比组内 baseline 更准经过 value pretrain 与高频更新的 critic 给出的 advantage 比 GRPO 的组内统计 baseline 更准，single-rollout 的 variance 劣势被补平
