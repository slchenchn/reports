    02
    Origin

    这个词先是经验判断，后来变成工程范式

    Mitchell Hashimoto

    从重复错误里提炼机制

    在 My AI Adoption Journey 中，Harness 的朴素定义是：agent 重复犯错时，把修复固化成系统性的预防措施

    OpenAI

    把开发重心转向基础设施

    OpenAI 的实践 把它推进成 agent-first 产品开发流程：人主要构建 agent 能持续工作的环境

    核心变化不是“prompt 写得更长”，而是把对话里的临时修补推进到 repo 内可版本化、可复用、可验证的机制

    04
    Control Loop

    Harness 本质是闭环控制系统

    Guides · 前馈控制

    在动手前收窄搜索空间

    • AGENTS.md 作为入口地图
    • ARCHITECTURE.md 解释模块边界
    • schema、skills、脚本沉淀可执行约束
    ↔
    Sensors · 反馈控制

    在动手后发现偏差并推动自修复

    • lint、编译检查、测试过滤
    • 安全/策略扫描、review agent
    • Playwright 截图、日志、trace

    从 ThoughtWorks 的梳理 看，Harness 不是替模型思考，而是把高方差系统压到可控区间里

    05
    Why It Matters

    长期维护能力不是一次性正确率

    只有少数模型在 zero regression rate 上超过 50%

    SWE-CI 把 agent 放进真实仓库的多轮 CI 演化过程里，评估的是持续改代码、跑测试、避免回归的能力。吞吐上去后，没有 Harness 的代码库很快会累积结构性熵

    06
    Workflow Shift

    Agent 会把治理成本前置到小项目阶段

    过去团队变大才暴露的问题，现在会被 agent 吞吐提前放大

    • CI/CD 不稳定会直接变成 agent 的噪声源
    • 代码质量规则不明确，agent 会在风格和边界上随机游走
    • 领域边界模糊，修复循环会把局部问题扩散成架构漂移
    • 可观察性不足时，模型容易过早宣布完成
    07
    Five Principles

    OpenAI 的五条原则，本质都是把隐性知识物理化

    What the agent can't see doesn't exist

    Slack 讨论、设计决策、schema 必须沉淀为 repo 内 artifact

    知识可见

    Ask what capability is missing

    优先把错误归因为环境缺能力，而不是让人手动兜底

    能力补齐

    Mechanical enforcement

    文档防君子不防 agent，用 lint、CI 和结构约束强制边界

    机械执行

    Give the agent eyes

    动态行为要靠截图、日志、trace 和可重复探针来验证

    可观察

    A map, not a manual

    入口文件要薄，细节按需加载，避免巨型手册污染 context

    08
    LangChain Case

    不换模型，只改 Harness，也能带来明显增益

    52.8% → 66.5% Terminal Bench 2.0，提升 13.7 个百分点

    LoopDetectionMiddleware

    追踪文件编辑次数，超过阈值后提示 agent 重新评估当前路径

    PreCompletionChecklistMiddleware

    退出前拦截，强制对照任务规格运行验证，降低过早收尾概率

    Trace Analyzer Skill

    拉取 LangSmith trace，派生并行分析 agent，再汇总失败模式

    案例来自 LangChain 的 Harness Engineering 实践

    09
    Failure Modes

    常见失败模式都不是单靠更会说话能解决的

    01

    上下文越长 agent 越笨

    无关搜索结果和长日志挤占注意力，应该限制注入量，用过滤测试替代全量噪声

    02

    AGENTS.md 越长效果越差

    巨型说明书不可验证，入口文件应削薄成目录，细则下沉到模块文档

    03

    agent 总说自己已经搞定了

    模型自评有正向偏误，需要独立 evaluator，如强制截图校验或 trace 检查

    04

    合并快但代码库越来越脏

    吞吐提高后熵管理要单独成 lane，用自动化定期扫除无效抽象

    10
    Counterintuitive

    更多 instruction 不一定更好，信号密度才重要

    LLM 生成的 agentfile 可能稀释真正有用的约束

    • ETH Zurich 对 138 个 agentfile 的研究 发现，LLM 生成 agentfile 对性能有负面影响
    • 原因不是“文档没用”，而是泛泛最佳实践会淹没具体代码库的关键约束
    • 人工文件设计不佳时也只带来约 4% 提升，因为描述性文档不能直接改变决策路径
    11
    Cold Start

    Harness 建立初期，效率往往低于人工

    缺什么就卡什么

    • 没有自动化验证，agent 会在修复循环里打转
    • lint 规则不清，输出会持续漂移
    • 领域边界模糊，幻觉代码更难被提前拦截

    稳态后才出现复合收益

    OpenAI 报告的约 10x 效率提升 是 Harness 成熟后的结果。前期的基础设施开销会压低短期产出，但每个新增工程师都会复用同一套能力边界

    12
    Throughput Tradeoff

    极高并发下，Gatekeeper 模式会变成瓶颈

    传统模式

    防错优先

    单次修改成本高，准入卡点严格，等待阻塞的成本相对可接受

    高吞吐模式

    容错优先

    依赖快速 merge、快速发现、快速回滚。局部丑陋可以容忍，过早抽象反而会放大返工

    Three similar lines of code is better than a premature abstraction

    13
    Depreciation

    Harness 也会折旧，需要版本化和清理

    今天有效的 guardrail，可能只是在绕开当前模型的短板

    • loop detection 针对盲目重试
    • 退出前 checklist 针对过早收尾
    • 时间提示针对低估耗时
    • 模型变强后，补丁可能从约束变成噪声
    14
    Where It Goes

    未来 Harness 会从手写规则走向协同演化

    01

    半自动生成

    agent 从历史日志里反思失败模式，提出 hooks、checklist、evaluator 候选，再由人决定是否固化

    02

    Agent Team Harness

    多 agent 并行后，关键问题会变成任务边界、文件所有权、交接协议和冲突检测

    03

    架构面向 agent 可读

    选框架、目录、schema、日志和测试策略时，会同时考虑人是否好维护、agent 是否容易验证

    15
    Takeaway

    Harness Engineering 不是让 prompt 更长，而是把经验变成 agent 能执行、能看见、能自我修复的工程系统

    当模型能力继续上升，真正拉开差距的是组织能否把失败沉淀成闭环
