# LLM 推理服务限流策略

## 为什么首版不做 per-user

首版先不做 per-user，不是因为公平性不重要，而是因为现在没有看到足够成熟、可直接复用的做法

公开可见的 Coding Plan 产品，成熟做法主要集中在两类事情

- 用套餐和平台规则约束总体负载形态
- 在系统负载变坏时，由平台侧做体验保护

但它们很少公开 per-user 的细规则，更没有一套可以直接搬到内部自部署场景的标准方法

所以对我们当前阶段，更合理的起点不是先把 per-user 规则做复杂，而是先回答一个更直接的问题：**系统体验开始恶化时，网关要不要继续把新请求送进 vLLM**

## 问题边界

这里讨论的不是“要不要排队”

排队本来就是 vLLM 在做。请求一旦被放进 vLLM，它就会进入内部 waiting queue，等待被调度

我们现在讨论的是另一层决策：**网关是否还要继续接收新请求，并把它们送进这个 queue**

所以这篇文档讨论的不是“去掉排队”，而是

- vLLM 内部排队继续存在
- 当实时体验已经变坏时，网关停止继续喂新请求
- 用硬 reject 把 queue 的继续扩张截断

这也是为什么问题本质上是 admission control，而不是 scheduler 改造

vLLM 当前也没有成熟的内建硬 reject 方案。[Issue #13395](https://github.com/vllm-project/vllm/issues/13395) 在 2025 年 2 月 17 日提出“busy 时能不能 reject request”，最终被 `Closed as not planned`。[RFC #18826](https://github.com/vllm-project/vllm/issues/18826) 在 2025 年 5 月 28 日提出 waiting queue 上限，到 2026 年 4 月 17 日仍然没有合并

## 外部参考：Coding Plan 厂商公开承诺了什么

### 总体结论

先说结论：**目前公开资料里，几家主流 Coding Plan 厂商几乎都没有给出数值化的 TTFT / TPOT 承诺**

它们公开表达的内容，更多是下面几类

- 低延迟、稳定、流式输出不中断这类定性承诺
- 高峰时平台会做保护，而不是无限放流量
- 高档位套餐拥有更高 TPM 或更稳定体验

也就是说，外部参考给我们的启发，不是“别人把 TTFT 承诺成了多少毫秒”，而是**别人也在把体验保护放在平台侧动态完成，只是很少把指标公开量化**

### 阿里云百炼

[阿里云百炼 Coding Plan 概述](https://help.aliyun.com/zh/model-studio/coding-plan) 公开了套餐、模型、工具接入和使用边界，但当前官方文档没有看到数值化的 TTFT / TPOT 承诺

从公开文档能读到的重点是

- Coding Plan 是 AI 编程场景专用产品，不是通用 API 入口
- 平台重点强调的是专属入口、固定月费、模型调用次数扣减和使用边界
- 当前公开资料没有把“好体验”明确写成 TTFT / TPOT 数字

对我们有用的结论不是某个具体数字，而是：**阿里的公开产品表述里，Coding Plan 也没有把体验保护写成一套静态 latency SLA**

### 腾讯云

[腾讯云 Coding Plan FAQ](https://cloud.tencent.com/document/product/1772/128997) 里最值得注意的两句是

- `Coding Plan 没有额外的并发请求数限制`
- 429 `tpm rate limit exceeded` 的可能原因是 `系统负载高触发限流`

这组表述非常关键

它说明腾讯公开承认了一件事：即使没有显式并发上限，平台在系统负载高的时候，仍然会主动做保护

但同样地，腾讯当前公开材料也没有给出数值化的 TTFT / TPOT 承诺

所以腾讯给我们的参考不是某个 latency 数值，而是更重要的策略方向：**正常时不必写死并发阈值，系统负载高时由平台侧动态触发保护**

### 火山方舟

火山方舟这块公开表述离我们的问题最近，但仍然主要是定性承诺，而不是数值承诺

在火山引擎官网文章 [《火山方舟Coding Plan：低延迟代码补全提升开发效率》](https://www.volcengine.com/article/37554) 里，官方公开写了几件事

- 提供 `稳定的低延迟代码补全体验`
- `不会因平台调用高峰而出现明显降速`
- Pro 套餐 `TPM更高`，适配高强度编码场景下的低延迟
- Auto 调度会基于 `效果 + 速度` 匹配模型组合

这已经是目前能看到的最接近 latency 承诺的公开表达了

但要注意，它依然不是数值化 TTFT / TPOT 承诺，而是定性表述

所以火山给我们的参考也不是“TTFT 承诺 1 秒内”这种数字，而是：**平台明确把低延迟和高峰稳定性当成目标，并通过平台侧调度和保护机制来实现**

### 小结

把三家放在一起，当前公开资料的共同点其实很清楚

| 厂商 | 是否公开数值化 TTFT / TPOT 承诺 | 公开表达更像什么 |
| --- | --- | --- |
| 阿里云百炼 | 没看到 | 场景边界 + 套餐规则 |
| 腾讯云 | 没看到 | 系统负载高时平台触发保护 |
| 火山方舟 | 没看到 | 低延迟、稳定、高峰不明显降速这类定性承诺 |

所以外部参考真正支持的不是“抄一个固定 latency 数值”，而是下面这件事

**Coding Plan 厂商公开承诺体验时，更多依赖平台侧动态保护，而不是公开一个静态 TTFT / TPOT SLA**

## 我们的策略

### 正确的问题应该怎么问

既然 queue 在 vLLM 内部持续存在，问题就不该表述成“系统要不要排队”

更准确的表述是

**当 TTFT、TPOT、latency 已经开始恶化时，网关还要不要继续把新请求送进 vLLM 的 queue**

我的结论是不要

因为一旦实时体验已经坏了，继续让新请求进入 vLLM，不是在“多服务几个请求”，而是在继续拉长 queue，把已经在线的请求一起拖慢

### 正确方案

首版策略应该直接写成下面这句

**不做 per-user，只做全局；全局限流不依赖预先压测出来的固定并发拐点，而是由 LiteLLM 持续观测实时 TTFT、TPOT、latency，一旦这些指标异常，就在网关层触发硬 reject**

这里的关键点有三个

- 观察的是**实时体验**
- 动作发生在**网关层**
- 被截断的是**进入 vLLM queue 的新增请求**

### 为什么要按实时体验触发

因为 coding agent 的负载太不均匀，静态并发值本身不稳定

- 请求的 context 长度变化很大
- 不同任务的工具调用链长度差异很大
- 不同模型、不同任务类型对 TTFT 和 TPOT 的压力不一样
- 同样的并发数，在不同时间段未必代表同样的体验压力

所以更靠谱的做法不是先猜一个固定拐点，再长期用这个拐点当真理

更靠谱的做法是直接承认：**真正需要保护的是体验，而不是某个离线 benchmark 上算出来的并发数**

### 这套策略在行为上意味着什么

系统正常时

- 请求照常进入 LiteLLM
- LiteLLM 照常把请求送进 vLLM
- vLLM 照常完成内部排队和调度

系统异常时

- 旧请求继续在 vLLM 里排队和执行
- 新请求不再继续被送进 vLLM
- 网关通过硬 reject 阻止 queue 进一步变长

所以这套策略不是取消 vLLM 的 queue，而是当 queue 已经开始伤害体验时，不再继续扩大它

### 这套策略的核心原则

如果压成一句话，就是

**用实时体验决定 admission，而不是用固定并发数猜 admission**

这也是目前外部 Coding Plan 公开实践里最值得借鉴的部分

- 很少有人公开承诺数值化 TTFT / TPOT
- 但大家都在用平台侧机制保护交互体验
- 真正起决定作用的是“系统现在是不是已经开始变坏”，而不是“离线压测时某个并发数曾经安全”

## 待定事项

- [ ] 需要先明确内部认定的 TTFT、TPOT、latency 异常区间
- [ ] 需要明确异常是看瞬时值，还是看最近窗口聚合值
- [ ] 需要明确什么条件下恢复放流，避免在保护态和正常态之间来回抖动
- [ ] 需要在有了足够真实流量之后，再决定是否有必要补 per-user 规则
